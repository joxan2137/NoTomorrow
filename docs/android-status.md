## 2. How to build and run

```bash
export JAVA_HOME=/opt/homebrew/opt/openjdk@21     # 21.0.12.1; required — the wrapper needs >= 17
cd /Users/joxan/projects/NoTomorrow/android

# android/local.properties (untracked, already present on this machine):
#   sdk.dir=/opt/homebrew/share/android-commandlinetools

./gradlew :app:compileDebugKotlin      # fast syntax gate
./gradlew :app:testDebugUnitTest       # 299 tests
./gradlew :app:assembleDebug           # -> app/build/outputs/apk/debug/app-debug.apk
adb -s emulator-5554 install -r app/build/outputs/apk/debug/app-debug.apk
adb -s emulator-5554 shell am start -n app.notomorrow.android/app.notomorrow.MainActivity
```

`adb`, `avdmanager` and `sdkmanager` are on `PATH` via `/opt/homebrew/bin`; the emulator binary is
at `/opt/homebrew/share/android-commandlinetools/emulator/emulator` (not on `PATH`).

### The `nt402` AVD — sized to overlay the iOS captures

`~/.android/avd/nt402.avd/config.ini`:

```
hw.lcd.width  = 1206
hw.lcd.height = 2622
hw.lcd.density = 480          # 3.0 px/dp  ->  402 x 874 dp
image.sysdir.1 = system-images/android-36/google_apis/arm64-v8a/
abi.type = arm64-v8a ; tag.id = google_apis ; hw.ramSize = 3072
```

1206 × 2622 px at 480 dpi is **402 × 874 dp**, which is exactly the iPhone reference's 402 × 874 pt
at @3x. Android and iOS screenshots are therefore the same pixel dimensions and can be diffed
without rescaling — every measurement in §3 is in raw pixels at 3 px per point/dp.

Capture with `adb -s emulator-5554 exec-out screencap -p > shot.png`; the iOS side used
`xcrun simctl io <udid> screenshot`.

#### The platform top inset is not a deviation

Five round-2 reviewers independently measured the whole Android page sitting 49–51 px above iOS
and each verified it is the device inset, not a layout bug: Android's `statusBars` inset is 136 px
(`dumpsys`) against the iPhone's 186 px, and both platforms place the header the same 24 px (8 dp)
below it. After a +49…+51 px shift the structural bands match one-for-one. Every y-coordinate
quoted in the tables below is raw, un-shifted pixels unless it says otherwise.

### Caveats on the numbers

1. **Round-0 captures 06–20 were taken with glass disabled.** Per
   `design/parity/android/CAPTURE-NOTES.txt`, a one-line local patch
   (`RootScreen.kt:72 LocalNtBackdrop provides backdrop → null`) was needed because the unpatched
   build drew the entire post-onboarding UI as an empty `ground` rectangle. Glass surfaces in
   06–20 therefore show their flat fill; layout, type and colour are the real build.
   `06-dashboard-realglass.png` is the one unpatched frame that rendered. **That blocker is fixed**
   — `NtBackdrop.kt:60` latches `captureFailed` when the `record` throws and `RootScreen.kt:75`
   degrades to `GlassTier.Tint` instead of losing the screen — and round-1 captures came from the
   unpatched build.
2. **The round-1 hypothesis that `captureFailed → GlassTier.Tint` was latching on this emulator is
   retired.** It was wrong. The fallback never fired; the recording was silently *empty*. §4 has
   the mechanism. Nothing about the flat glass depended on the emulator, so nothing here waits on

## 4. Known gaps / not reproduced

### What round 2 changed

**The in-window overlay host — menus, alerts and action sheets no longer live in a `Popup`.**
`designsystem/NtOverlay.kt` (120 lines) hosts one `NtOverlayState` per window; `RootScreen.kt:97`
composes `NtOverlayHost(overlay)` as a sibling of `NtNavHost`, **after** the subtree that records
the backdrop and inside the same window, so anything registered through `NtOverlayContent` draws
above every screen and above the tab bar while still being able to sample it. `NtMenu`, `NtAlert`
and `NtActionSheet` keep their public signatures and now take that path: no menu scrim, a 0.48
alert scrim, no action-sheet scrim, tap-outside dismiss, `safeDrawing` (IME) insets on the centred
panel, anchor capture via `onGloballyPositioned` on a zero-size probe reading
`parentLayoutCoordinates`, and the iOS scale/fade curves. A `Popup`/`Dialog` fallback remains for
call sites *inside* a sheet, where `currentNtOverlayHost` returns `null` — a `ModalBottomSheet` is
its own window stacked above this host, so a panel drawn here would be hidden behind it. Those
sites render the same measured flat fill. The reasoning is recorded in `android-glass.md` §6.

**But the overlay host was not the flat-glass root cause — it already existed and already worked.**
`LiquidGlass`'s same-window and sampleable checks were passing and the shader was running.
`NtBackdrop.kt` recorded *nothing*: it called
`backdrop.layer.record(this, layoutDirection, target) { drawRect(ground); drawContent() }` — the
`GraphicsLayer.record(density, layoutDirection, size)` **member**, which records with the layer's
own `CanvasDrawScope`. `drawContent()` inside that block still paints into the screen canvas the
`ContentDrawScope` holds, so the layer came back holding only the `drawRect(ground)`, and every
sampler evaluated `transfer(uniform ground)` and produced a constant. The fix is one line —
`backdrop.layer.record(target) { … }` at `NtBackdrop.kt:143`, `DrawScope`'s member-*extension*,
which `LayoutNodeDrawScope` overrides precisely to swap its canvas for the layer's first. The
same mechanism explains the round-0 symptom in §3 caveat 1 (the block drew the recording instead
of the content, so the app rendered as a bare `#0A0A0B` rectangle). This is why 15 went 78 → 95
and 16 went 71 → 87 — see §3 for the luminance measurements that confirm sampling.

**Typography — the width ramp is fitted, not guessed.** `scripts/fit_font_width.py` (new, 24 KB,
self-contained, `--validate` / `--tracking` / `--opsz` flags) threshold-scans the ink extent of
**73 reference strings** out of `design/parity/{ios,android-r1}/*.png` across screens 06, 07, 09,
10, 11, 12, 14, 18, 19 (bright text at L > 70; dark-on-white pill labels at L < 120 over detected
pill-interior rows, discarding runs that touch the capsule ends), instantiates Roboto Flex with
`fontTools.varLib.instancer` at candidate `(wdth, XTRA, opsz, wght)` locations — cached under
`build/fontfit`, gitignored — measures each string with `PIL.ImageFont.getbbox` at exactly
3 px/pt plus `letterSpacing × (len − 1)`, and uses the model only as a **ratio** against the same
string's round-1 width so PIL hinting, the missing HarfBuzz kerning and the scan threshold all
cancel. Round 1 had assumed "+6 `wdth` ≈ +6 % advance"; measured on the instanced font, 6 units
buy **~1.3 %**, which is why its three hand-picked buckets (106 / 100 / 97) left the build 3–9 %
narrow. The fitted per-style ramp is **`wdth` 96.2 … 125.2**, with `opsz` mirroring SF Pro's own
optical split — pinned to Roboto Flex's text default 14 below 20 pt, equal to the point size above
it. Per-style RMS relative width error, before → after: `largeTitle` 3.19 → 1.47 %, `headline`
3.77 → 2.25 %, `body` 3.89 → 1.89 %, `subheadline` 3.36 → 1.71 %, `subheadlineBold` 5.06 → 1.79 %,
`footnote` 4.79 → 1.87 %, `caption` 3.59 → 1.27 %, `eyebrow` 3.92 → 1.88 %. Re-measured on the
emulator over 42 of those strings: **4.12 % → 1.85 %**, mean bias within ±0.4 % for `headline`,
`body` and `largeTitle`. The full table, the four interpolated rows (`title1`, `title3`,
`callout`, `footnoteBold` — no reference string exists for them in any capture) and the −3.0…−1.3
display-row device correction are in the block comment at `designsystem/NT.kt:167-236`.
`letterSpacing` was left at `Theme.swift`'s own values for all 13 styles: the joint `(wdth,
dTrack)` fit picked `dTrack = 0` everywhere, so re-tracking would change the letter rhythm to buy
less than the per-glyph noise. `XTRA` stays at 468 (it opens counters, not advances; a
`wdth 112 + XTRA 540` trial read visibly rounder than SF Pro), and `wheelDigit` stays at
`wdth 100 / opsz 14`, measured directly off `design/ios26-reference/11-wheel-schedule-editor.png`.

**Sheets — the presenting screen is not transformed, and the nested scrim was too dark.** Fitting
`06-dashboard.png → 19-cant-make-it.png` over the 114 167 content pixels above the sheet gives a
pure sRGB multiply `k = 0.5188` (α 0.48, the view tree's `UIDimmingView`) at 0.56/255 mean-abs
residual (p99 0.71), and `17 → 18` gives `k = 0.7114` (**α 0.2886**) at 0.19/255 over 600 294
pixels. So iOS 26 dropped the iOS 13–18 card push-back for these sheets — **no scale, no
translation** — and `NtSheetPresenter`'s planned `graphicsLayer` hook was measured as identity and
not built. What *was* wrong is that Android stacked two 0.48 scrims and rendered the food-search
card behind the portion sheet at 0.478 instead of 0.289; `Sheets.kt:181` now returns `0.2886f` for
depth > 0. Sheet card geometry was also corrected: the card bottom is 2598 px (866 pt, the 8 pt
partial inset) in every capture, and a `.height(N)` detent renders **N + 17.67 pt** of card, so
`height = ` now adds that bleed while `navigationBarsPadding()` takes it back off the content.
`minHeight = ` deliberately does **not** get the bleed: iOS's two-detent `[.height(660), .large]`
card measures 666.33 pt, only 6.33 pt over its detent, so adding 17.67 would overshoot by 29 px
instead of undershooting by 19 (`Sheets.kt:400-420`). One known residual: iOS's nested scrim
starts exactly at the presenting sheet's top edge (y = 186 — rows 150–180 are identical in 17 and
18), while Android's `ModalBottomSheet` scrim covers the whole window, so that strip reads ~(4,4,4)
instead of (5,5,6). 1–2 levels in a near-black strip; left alone.

**Icons — `NtIcons.glyphScale`.** An SF Symbol's ink legitimately overflows its point box
(`person.2` at 28 pt paints 31 pt wide) while a 24-unit Material-style viewport is by construction
inside it, so the five tab glyphs measured 12–17 % small in an identical 28 dp box. `Icons.kt` now
carries a per-symbol `glyphScale` (House 1.18, Dumbbell 1.05, ForkKnife 1.145, Person2 1.21,
Person2Outline 1.19, everything else 1.0) and `NtIcon` keeps the caller's **layout** size while
drawing the painter into a centred `requiredSize(size * glyphScale)` box — no call site moves,
nothing is resampled (the vector rasterises at its drawn size, not through a `graphicsLayer`
upscale), and the ratio is a property of the symbol so it holds at every size. Icons at
`glyphScale == 1f` take the original code path untouched. No drawable XML was changed, which is
why glyph *shape* remains in the §3 table. Verified on the emulator: house 81×73, dumbbell 86×52,
fork-knife 47×79, chart 74×63, `person.2` 94×62.
