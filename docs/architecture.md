# No Tomorrow — iOS architecture and implementation contract

Read this before touching any feature. The prototypes in `design/*.dc.html` are the visual spec; this file is the code spec.

## Stack

- SwiftUI, iOS 17+, Swift 5 language mode, `@Observable` for view state, SwiftData for persistence.
- Project is generated by XcodeGen from `project.yml`. Files are picked up by folder: anything under `NoTomorrow/` joins the app target, `NoTomorrowWidgets/` the Live Activity extension, `Shared/` both. Never edit `NoTomorrow.xcodeproj` by hand; run `xcodegen generate` after adding folders (adding files to existing folders needs no regeneration).
- Type-check fast with `scripts/typecheck.sh` (whole app module, ~7 s, safe to run in parallel). Full build: `xcodebuild -project NoTomorrow.xcodeproj -scheme NoTomorrow -destination 'id=<sim udid>' -derivedDataPath build/DerivedData build`.
- Dark-only. Never use `.primary`/`.secondary` system colors or `Color(.systemBackground)`; use `NT.Colors.*`.

## Folders

```
NoTomorrow/App            NoTomorrowApp (StoreLoader, environment objects), RootView (store error vs onboarding vs tabs, routes),
                          AppState, NotificationRouter, StoreLoader + StoreErrorView
NoTomorrow/DesignSystem   Theme.swift (NT.Colors/Fonts/Spacing/Radius/Size), Components.swift (buttons, cards, chips, rings, rows)
NoTomorrow/Models         Models.swift — every @Model + enums; NoTomorrowSchema.models
NoTomorrow/Services       RestTimerController, WorkoutSessionController, ExerciseLibrary, Formatters (Fmt), + per-feature services
NoTomorrow/Features/<X>   one folder per tab/flow; each owns its views + view models
NoTomorrow/Resources      Localizable.xcstrings (en + pl), exercises.json, Fonts, Assets
Shared                    RestTimerAttributes (ActivityKit payload)
NoTomorrowWidgets         Live Activity UI
backend/data/ai           estimate-spec.json, bundled into the app (AI prompts, schemas, limits); fixtures/ join the test target
```

`Features/Placeholders.swift` holds stand-in views (`DashboardView`, `TrainView`, `FuelHomeView`, `ProgressHomeView`, `BroView`, `OnboardingFlow`). When you implement one, DELETE its stand-in from that file and create the real type with the SAME NAME in your feature folder. Do not rename these entry types; `RootView` references them.

## Environment objects available in every view

```swift
@Environment(AppState.self) var appState                 // selectedTab, hasOnboarded, pendingRoute, openFuelToday()
@Environment(RestTimerController.self) var restTimer     // start(seconds:exerciseName:nextSetLabel:workoutName:), adjust(by:), skip(), finishIfElapsed(), remaining, progress, isRunning
@Environment(WorkoutSessionController.self) var session  // see "Workout session" under Train
@Environment(StoreLoader.self) var store                 // isOpen, failure, retry(), startFresh(), generation
@Environment(\.modelContext) var modelContext
```

Query SwiftData with `@Query` in views or `FetchDescriptor` in view models. `UserProfile` and `GymSchedule` are singletons: fetch the first, create if missing (onboarding creates them).

## App shell, store and routing

- **Store.** `StoreLoader` opens the SwiftData store (`ModelConfiguration("NoTomorrow")`). A store that fails to open is never swapped for an in-memory one: `RootView` shows `StoreErrorView` instead of onboarding or the tabs, with Try again (`retry()`), Save a copy of the data (share sheet with the store, `-wal` and `-shm`) and Start with empty data (confirmation, then `startFresh()` moves every store file into `Application Support/Store backups/<yyyy-MM-dd HH.mm.ss>/`, opens an empty store and sets `hasOnboarded = false`). Nothing is ever deleted, so a later build that fixes the cause opens the untouched store. Launch work (library import, routine seeding, the one-time rest-inherit pass) runs in `.task(id: store.generation)` and reruns after a recovery. There is no `VersionedSchema` yet; the first model change adds one.
- **Exercise library.** `ExerciseLibrary.importIfNeeded` runs on the main actor with the main context (the JSON is decoded off the main thread). It imports and backfills `namePL` when `nt.exerciseLibrary.version` differs from `libraryVersion` **or** there are no non-custom rows, and writes the stamp only after a successful save. Bump `libraryVersion` whenever `exercises.json` or `exercises_pl.json` changes.
- **Routes.** `AppState.Route` (`restTimer | activeWorkout | bro | settings`) is consumed by `MainTabView`. Sources: the `notomorrow://` URL scheme (`CFBundleURLTypes` in `project.yml`; `workout` → activeWorkout, `workout/rest` → restTimer, `bro`, `settings`; the Live Activity's `widgetURL` is `notomorrow://workout/rest`) and `NotificationRouter`, the `UNUserNotificationCenter` delegate installed by `AppDelegate`, which buffers routes until the shell connects. `activeWorkout`/`restTimer` expand the workout over the current tab (plus the rest sheet while the rest is running), `bro` selects Bro, `settings` selects Today.

## Design rules (from the canvas)

- Screen background `NT.Colors.ground`; 20 pt horizontal padding (`NT.Spacing.screenH`); sections separated by whitespace or `Hairline()`, not by cards. One focal card per screen for the object that matters: `FocalCard` (surface, a faint ember wash from the top-trailing corner, an ember hairline) for the next session, Train's Up next routine, the selected lift on Progress and Bro's shared week; plain `NTCard` for the single object of a sheet or a secondary block (portion sheet, code, Muscles this week).
- Type: `NT.Fonts.largeTitle` for tab titles with an `eyebrow()` line above (date, context); `headline` for section titles; `subheadline`/`footnote` in `ink2` for secondary; `NT.Fonts.display(n)` ONLY for hero numbers (time, kcal left, e1RM, volume) and the wordmark. Numbers in columns or that tick get `.tabular()`.
- Buttons: `PrimaryButton` (white) is the one thing to do; `SecondaryButton` (surface-2) beside it, equal widths in a card row (52 pt), 56 pt for full-width bottom CTAs; `GhostButton` for tertiary. Never an icon inside a card-row button.
- Ember (`NT.Colors.ember`) only for: next-session / Up next eyebrows, your who-trained dot and attended checks, progress lines and rings (and the rest countdown next to them), PR badges/trophies, streak icon, the Fuel history heat scale (`NT.Colors.heat`), and one-line warning captions under a form (bad check digit, store label, "check the numbers", workout ending in the future). Green = confirmed and your partner, rose = missed/destructive. Food macros have their own hues (`NT.Colors.protein` #5EB8FF, `carbs` #F5C04A, `fat` #B18CFF) and nothing else uses them: `MacroRing` (the kcal ring split by where the calories came from, 4/4/9 kcal per gram), the macro bars, the protein-to-go hint. Everything else white/grey.
- Hit targets ≥ 44 pt (wrap small visuals in a 44 pt frame with `.contentShape`). No fake status bar. Respect safe areas; content scrolls under the tab bar.
- Every string through the catalog: `Text("key")` with keys from `Localizable.xcstrings`; add new keys with BOTH `en` and `pl` values (Polish: sentence case, "ty" form, no gendered past tense, decimal comma comes free from formatters). Use `Fmt` for numbers/dates.
- `Fmt` also has `elapsed` (m:ss, h:mm:ss from one hour), `dayTitle(_:now:)` (Today / Yesterday / short date, + year outside the current one), `monthShort`, `percent`, `volume(_:unit:withUnit:)`, `lbPerKg`. Polish durations use "h" ("1 h 12 min", "za 2 h 5 min"). `StatTile` values shrink to 60 % instead of truncating. Typed numbers in the Fuel edit sheets parse with `NumberInput` (comma or dot; spaces, NBSP and thin spaces stripped; the whole text must be a finite number), the same rule as Android's `Parsing`.
- Empty states are designed, not blank: one line of copy + the action.

## Feature contracts

### Onboarding (`Features/Onboarding`) — `OnboardingFlow`
Three steps with a 3-segment progress bar and back arrow: You (name, body weight + kg/lb, goal chips, suggested daily target card computed by `TargetCalculator`), Schedule (7 day toggles Mon-first, wheel time picker, two reminder toggles), Pair (code card with share, "or enter your bro's code", Continue, "Not now"). Welcome screen before step 1: wordmark, tagline, language segmented control (English / Polski → `appState.languageOverride` "en"/"pl"), Get started. On finish: insert `UserProfile` + `GymSchedule`, set `appState.hasOnboarded = true`.
`TargetCalculator`: Mifflin–St Jeor with assumed 30 y / 178 cm when unknown, activity 1.55, +300 kcal build / −400 lose / 0 maintain; protein 2.2 g/kg build, 2.4 lose, 1.8 maintain; fat 0.9 g/kg; carbs = rest. Round kcal to 50.

### Dashboard (`Features/Dashboard`) — `DashboardView`
Eyebrow date + "Today" large title + avatar (opens `SettingsView` sheet). Week strip (Mon–Sun of current ISO week): letter labels from `weekday.*` keys; attended = ember ring + check; missed = rose ring + x; today = white filled circle; a gym day still ahead (planned or confirmed, not today) = thin `border` ring around an `ink` number. Under each circle a 5 pt row of who-trained dots (`WeekStripView.dots`): ember when you attended, and when paired green when your partner attended or rose when they missed/cancelled (the accessibility label adds "dashboard.week.partnerDone %@"). Next-session card (the screen's `FocalCard`): eyebrow "dashboard.nextSession" + routine name; hero time `display(64)`; relative day + countdown (`Fmt.relativeDay`, `Fmt.countdown`); bro row (state machine: no bro → "dashboard.noBro"; bro in, me not → "dashboard.broIsIn %@" with green dot and time; both in → "dashboard.bothIn" with both times); button row: not confirmed → `I'm in` + `Can't make it`; confirmed → `Start workout` (or `Back to workout` if a session is active, which expands the running workout over Today; nothing here switches tabs) + `Can't make it`. Rest day → the card shows the next gym day instead. Fuel summary row (`MacroRing` 64 pt with kcal left + "left", three `MacroBar`s in the macro hues) calls `appState.openFuelToday()`, so Fuel always opens on today. Last session row: name · duration · "n PRs" ember, PR chips; tapping it opens that workout's `WorkoutDetailSheet` over Today (the Train tab only when there is no finished workout). `Can't make it` opens `CantMakeItSheet` (Bro feature).
Attendance: confirming writes/updates `AttendanceRecord(day: today, participant: .me, status: .confirmed)` (sent to the server only when paired). Finishing a workout with at least one completed set marks the day it **started** `.attended`, on any day (rest days, extra sessions and make-up days count; 22:30–00:20 counts for the evening). `AttendanceService` (Services) derives the strip states and sweeps misses incrementally: `markPastPlannedAsMissed` keeps a cursor in `nt.attendance.sweptThrough`; the first run only sets it to yesterday, later runs judge `max(cursor + 1, profile.createdAt, today − 30) … yesterday` (my planned/confirmed record on any day → missed; a gym day with no record → a missed row) and move it forward, so changing the gym days never rewrites the past. The 21:00 "did you skip?" check is a backend job.
Attendance sync: the user's attended/missed/planned writes reach the backend whenever they are signed in, paired or not, so a partner sees them and the server's reminder and 21:00 jobs stay quiet on a trained day. `AttendanceSync.report` hands each one to `BroService.reportAttendance`, which queues it in `AttendanceOutbox` (UserDefaults `nt.attendance.outbox`, JSON `[{day: "yyyy-MM-dd", status}]`, one entry per day, last write wins) and flushes; `BroService.refresh` flushes again after every successful `me()`. A 4xx other than 401/408/429 drops the entry, any other failure keeps it for the next refresh, and failures never show an error. Nothing is queued while signed out; Delete account clears the queue. Sources: Finish (`attended`) and workout edit/delete (via `AttendanceService.wireStatus`: attended/missed as written, a cleared gym day → `planned`, a cleared rest day → not sent, since the server has no delete).

### Train (`Features/Workout`) — `TrainView`, `ActiveWorkoutView`, `WorkoutMiniBar`, `ExercisePickerView`, `RestTimerView`, `WorkoutDoneView`, `WorkoutDetailSheet`
`TrainView`: routines list (seeded Push A / Pull A / Legs on first run by `RoutineSeeder` using exercise ids from exercises.json: "Barbell_Bench_Press_-_Medium_Grip", "Barbell_Shoulder_Press", "Incline_Dumbbell_Press", "Triceps_Pushdown", "Side_Lateral_Raise"; "Barbell_Deadlift", "Bent_Over_Barbell_Row", "Pullups", "Barbell_Curl", "Seated_Cable_Rows"; "Barbell_Squat", "Romanian_Deadlift", "Leg_Press", "Leg_Extensions", "Standing_Calf_Raises" — look up by id, skip missing). On top an Up next `FocalCard`: the routine Today suggests (`DashboardModel.suggestedRoutine`), eyebrow "train.upNext" + exercise count, the name in `title1`, one line per item (exercise · `targetSets × targetReps`), `PrimaryButton` "workout.start"; while a workout is in progress the eyebrow reads "workout.inProgress" and the button "dashboard.resumeWorkout" expands it. Below, the other routines, each with a 40 pt `surface2` play button (`StartPlayButton`); "Start empty workout"; history (most recent first, name · date · duration · volume · PRs) grouped under "workout.history.thisWeek" / "lastWeek" / "earlier" (`HistoryWeek`, ISO weeks), opening `WorkoutDetailSheet`. A workout in progress shows as the mini bar, not as a banner.
**Workout session.** `WorkoutSessionController` (`@MainActor`) is the single source of truth: the active `Workout.id` (persisted under `nt.workout.active`; the legacy `nt.activeWorkoutID` is migrated), `showsActiveWorkout` (expanded vs collapsed), `wantsRestSheet`, and one `ActiveWorkoutModel` per workout (`model(for:context:)`), so the open exercise, PR hint, up next and summary survive a collapse. `workout(in:)` resolves by id with no side effects (safe in a body); `activeWorkout(in:)` also adopts an unfinished workout, never a discarding one and never while a summary shows; `isWorkoutInProgress` = active and not on the summary. `discard` lets go at once and deletes 0.7 s later (pending ids persisted in `nt.workout.discarding`, finished on the next launch). `restore(in:)` runs from `MainTabView`: it finishes an interrupted discard and repairs orphans (keep the session's unfinished workout, else the newest; the others end at their last `completedAt` when they have completed sets and are deleted when not). A cold start with a workout running shows the mini bar and never auto-expands. The cover is resolved by id and holds its workout for the whole presentation.
**Starting.** Today and Train both go through `WorkoutStarter`. `gate` allows one workout at a time: Train shows a confirmation dialog (`workout.inProgress`: Resume, Discard it and start new — only when the running workout has 0 completed sets, also enforced by `discardAndStart` — and Cancel); Today's CTA just expands the running one. Nothing switches tabs. Each row copies the same row of the last *finished* session of that exercise; an exercise never done gets `RoutineItem.targetReps` × 0 kg. Today suggests the routine after the most recent finished workout whose name matches a routine (ad-hoc workouts do not shift the rotation). Rest: `UserProfile.defaultRestSeconds` (Settings › Rest timer); heavy compounds (id contains `squat`, `deadlift` or `bench_press`) get default + 30 s, capped at 600 s; `RoutineItem.restSeconds == 0` means "inherit the default at start" — the seeder writes 0, and a one-time pass (`nt.routines.inheritRest`) turned the legacy seeded 90/120 into 0. Exercises added mid-workout get the default too.
**Mini bar** (`WorkoutMiniBar`, a `safeAreaInset` on every tab while `session.isWorkoutInProgress`): 52 pt tall, 20 pt side margins, 8 pt above the tab bar; a Liquid Glass capsule on iOS 26, a `surface` capsule with a hairline and shadow on 17/18. Leading 8 pt ember dot, or a 24 pt `ProgressRing` (3 pt) while resting; line 1 the workout name (`subheadlineBold`); line 2 (`footnote` ink2, tabular) `Fmt.elapsed · current exercise`, or `timer.rest` + m:ss in ember · up next; trailing `chevron.up`, or while resting a `common.skip` ink capsule that calls `restTimer.skip()`. Tapping anywhere else expands. Hidden on the summary and while the keyboard is up; Fuel's add bar stacks above it. A shell-level `.restTimerExpiry()` closes a rest that ends while collapsed; in the foreground the "Rest is over" notification shows only while collapsed (full screen: haptic only).
`ActiveWorkoutView` (full-screen cover, `session.showsActiveWorkout`): header with a leading collapse button (`chevron.down`, 36 pt `surface2` circle in a 44 pt hit area, `workout.minimize`; not on the summary) + routine name + elapsed `Fmt.elapsed` (ember dot; h:mm:ss from one hour) + "Exercise i of n"; `Finish` (surface-2, 44 pt) → confirmation; under the header the exercise rail: one 4 pt capsule per exercise (16 pt tap target) filled in ember by its completed share of sets, the current one's track brighter, a tap opens that exercise; per exercise: name, "Last: 80 × 8" from the most recent completed set of that exercise in a previous workout; column header Set · Previous · kg/lb · Reps · ✓ (`.cap` ink2); set rows 44 pt (`SetCells`): set number (tap → menu W/D/F/normal, divider, Delete set), previous ghost value, two 60×44 numeric cells (`TextField` with `.keyboardType(.decimalPad)`, prefilled from previous), a 36 pt rounded check in a 48 pt column (ember with a dark check when done, `surface2` with an `ink3` check when not); a done row sits on a 7 % ember tint instead of being dimmed. **Suggested weight** (expanded exercise, above the column header): when the previous session of that exercise has ≥ 2 completed normal sets (not warm-ups, not drop sets) all at one weight > 0 and every one reached the routine's `targetReps` (the routine named like the workout) or, without a target, none has fewer reps than the first, the line shows "workout.suggest.try %@" (that weight + 2.5 kg, or + 5 lb) over "workout.suggest.last %@ %@" (reps · weight) and "workout.suggest.use", which sets every open normal set to it; the line shows only while an open normal set still has the previous weight (`ActiveWorkoutModel.suggestion`). Nothing changes a weight without the tap. Previous comes from the newest other *finished* workout with a completed working set of that exercise: warm-ups match its warm-ups in order, other rows its working set with the same number; past the end a working row shows the most recent completed working set and a warm-up nothing; the prefill touches open rows only. Ticking a set: sets `completedAt`, computes PR/set record via `RecordService`, shows the ember hint "workout.beatsBest", starts the rest timer with the exercise's `restSeconds` (skip auto-start if the NEXT set is a drop set). A row that would log 0 reps (no Previous to copy) logs nothing: warning haptic, focus to reps. Add set duplicates the last row; Delete set renumbers. Add exercise → `ExercisePickerView` sheet (multi-select). Rest timer pill floats above the bottom when `restTimer.isRunning` (ring, mm:ss, +15, Skip); tap → `RestTimerView` sheet with the 280 pt ring, `display(104)` time, −15 / Skip rest / +15, "Up next" card (next set target = last completed set of this exercise), lock-screen note. Finish stamps `endedAt` at once and saves (killing the app on the summary cannot stretch the duration), marks the start day `.attended` and reports it when at least one set was completed, and re-derives the records of the workout's exercises (`RecordService.rebuild`), then shows `WorkoutDoneView`: "DONE." display, volume `display(56)` + "kg moved"/"lb moved", delta vs the last workout with the same name, tiles Time/Sets/Exercises, "Records tonight" list (PRs ember trophy, set records grey medal) or the no-records line, Done. "Edit sets" clears `endedAt`; Done only releases the session.
Live Activity: `RestTimerAttributes` carries `workoutName` and the app-localized `restLabel` / `overLabel`; `ContentState` carries `endDate`, `exerciseName` and `nextSetLabel` (so ticking a set mid-rest updates "up next"). The countdown uses the fixed range `endDate − total … endDate` with `staleDate = endDate`, and a stale or ended activity shows `timer.notification.title`. Lock Screen and Dynamic Island open `notomorrow://workout/rest`. `RestTimerController` is `@MainActor` and serialises ActivityKit calls; a delivered "Rest is over" notification is removed when the next rest starts or on Skip.
**Units.** Weights are stored in kg. The whole workout area (set cells, Previous, "Last", PR hint, rest card, Live Activity label, summary hero/delta/records, history row, detail volume, Progress volume tiles) shows and parses the user's unit (lb = kg × `Fmt.lbPerKg` 2.2046226218, up to 2 decimals). Typed text is compared with the shown value in display space, so a converted display (60 kg as 132,28 lb) is never written back.
`ExercisePickerView`: search field, muscle chips (`ExerciseLibrary.MuscleGroup`), rows name + muscles + last set or "Never done", multi-select rings, exercises already in the workout show "In"; "Create "<query>" as a new exercise" row inserts a custom `Exercise` (id "custom-<uuid>", primaryMuscles from selected chip); bottom `Add n`. Search folds case and diacritics locale-independently and maps `ł` → `l` (`WorkoutStrings.fold`), so "lawka" finds "Ławka".
**Editing finished workouts** (`WorkoutDetailSheet` via `.workoutDetailSheet(_:unit:)`, opened from Train history and the Dashboard's Last session row). Read mode: name · Edit · Done, tiles (volume in the unit), PR line, a Notes block, set numbers that skip warm-ups. Edit mode, same sheet (`WorkoutEditView` + `WorkoutEditModel` over a plain-value `WorkoutDraft`): Cancel · "Edit workout" · Save, where Save needs a changed draft and a valid time (start ≤ now, end ≤ now + 60 s; otherwise the ember `workout.edit.endsInFuture` footnote). Details card: Name (empty keeps the old one), Date (≤ today), Start time, Duration (exact seconds until stepped; −/+ snap to the 5-minute grid, 5…720 min). Notes (3–8 lines). Every exercise expanded with a "…" menu (Move up/down, hidden at the ends; Remove exercise) and the `SetCells` table with a blank Previous column, rows never dimmed or locked, and Delete set in the kind menu; a row is logged only when `isDone && reps > 0`, and added rows (Add set copies the last row, a warm-up as normal; Add exercise takes the first working set of its last finished session) start done. Delete workout (red row, confirmation). Cancel with changes asks "Discard your changes?" (Discard changes / Keep editing); swipe-down is blocked only while dirty. Save (`WorkoutEditor.apply`) trims name and notes, sets `endedAt = start + duration`, remaps set times order-preserving (an untouched workout is the identity; rows with no time borrow a neighbour's), re-indexes, clears open rows, then rebuilds records for the exercises before ∪ after, corrects attendance, saves and posts `.workoutHistoryDidChange` (Progress reloads). Delete closes the sheet first, then deletes → rebuilds → corrects attendance → posts. Attendance correction: a workout counts on its start day when it has ≥ 1 completed set; the new counted day becomes attended (never a future day); the old one, unless another finished workout with a completed set started that day, becomes missed on a past gym day and loses my record on today or a rest day. The changes go to the server through `AttendanceSync`.
`RecordService` (Services): given a completed set, look at every earlier completed set of that exercise; PR = new max Epley e1RM or new max weight; set record = most reps at that weight. Marks `isPR` / `isSetRecord`. `rebuild(exerciseIDs:in:)` re-derives both flags for every set of the given exercises as if each completed working set had been ticked in `completedAt` order (pure `rebuildFlags`, same tie rule as `evaluate`; open sets, warm-ups and 0-rep sets get none) and writes only changed rows. It runs on Finish and after a finished workout is edited or deleted.

### Progress (`Features/Progress`) — `ProgressHomeView`, `ExerciseProgressView`
Home: eyebrow last PR date, "Progress" title, segmented Lifts / Body. Lifts tab (with completed sets): a scrolling row of `Chip`s, one per lift (first selected), over the selected lift's `FocalCard` — "progress.e1rm" eyebrow, current e1RM `display(56)` + unit, `ProgressDeltaChip` for the range, `E1RMChart` 160 pt (tap → `ExerciseProgressView`), `ProgressSegmented` 1M/3M/1Y/All; then "progress.musclesThisWeek" (`NTCard`): `MuscleHeatView` (the muscle-model regions filled with `NT.Colors.heat` by completed sets this ISO week: 0, 1–3, 4–6, 7–9, 10+; each set counts for every primary muscle of its exercise, `ProgressModel.buildMuscleWeek`), the five most-trained muscles with their counts, and "progress.notTrainedYet %@" for chest / shoulders / lats / quadriceps / hamstrings still at zero once anything was logged. Body tab: latest weight `display(40)`, 4-week trend delta, sparkline of raw (grey) + smoothed 7-day moving average (ember) using Swift Charts, "Log weight" sheet inserting `BodyWeightEntry`. Lifts list: every exercise with ≥1 completed set, sorted by last PR date desc: name, routine context/last PR, 72×24 sparkline of e1RM over time (ember if PR in last 30 days else grey), current e1RM + delta over the range. Tap → `ExerciseProgressView`: back + name + segmented 1M/3M/1Y/All; hero e1RM `display(64)` + delta chip; Swift Charts line+area of best e1RM per session with PR markers; tiles Last PR / This week volume / Sessions; weekly volume bar chart (all lifts, last 8 weeks, current bar ember); Records list (heaviest set, most reps) with dates. Empty state "progress.empty". Both screens reload on `.workoutHistoryDidChange` (a finished workout edited or deleted), and the volume tiles use the user's unit.

### Fuel (`Features/Fuel`) — `FuelHomeView`, `FuelCalendarSheet`, `FoodSearchView`, `PortionSheet`, `QuickAddSheet`, `BarcodeScannerView`, `ProductLabelSheet`, `AIScanView`
Home: a two-row header. Row 1: `‹ [▦ day ▾] ›` — 44 pt chevrons (`chevron.left/right` 15 pt semibold `ink`; forward disabled in `ink3 @ 0.4` on today) around a 32 pt `surface` date capsule (`calendar` icon, `Fmt.dayTitle` = Today / Yesterday / short date, plus the year outside the current one, `chevron.down`) that opens the History sheet; the group is pulled 12 pt left with negative leading padding; on a past day a trailing Today pill (`surface2`, `day.today`) fades in. Row 2: "Fuel" title + protein streak chip (target icon). Then the hero `MacroRing` 132 pt (10 pt, `surface` track) with kcal left `display(44)` + "fuel.kcalLeft", three `MacroBar`s in the macro hues, "eaten · goal" line; meals list Breakfast/Lunch/Snack/Dinner (entries as name · grams; kcal right; AI entries get an "est." `Badge`); the empty slot shows "fuel.nothingYet" + the "protein to go" hint in `protein`; bottom bar three 56 pt tiles: AI photo (white), Barcode, Search.
**Day navigation** (`FuelModel`): the chevrons, a horizontal swipe on the header or the hero (`DragGesture(minimumDistance: 40)`, horizontal-dominant), the Today pill and a History cell change the day, never past today, each with a `.selection` haptic; nothing else ticks. Midnight: `rolledDay(selected, previousToday, today)` follows to the new today when the old today (or a future day) was showing, otherwise keeps the browsed day; it runs on every Fuel appearance, on `.NSCalendarDayChanged` and on return to the foreground, and `today` is observable so the streak window moves. Snap-back: back in the foreground after **more than** 30 min in the background, a past day returns to today (the background stamp is used once). The Dashboard's Fuel row always lands on today (`AppState.fuelTodayRequests`).
**Day key.** `MealEntry.day` is local midnight at logging time. `FuelCalendar.dayKey(stored) = startOfDay(stored + 12 h)`, and a day's entries are fetched in `storedDayBounds(day) = [day − 12 h, nextDay − 12 h)`, so a time-zone change of less than ±12 h keeps every entry on its day. The streak and the grid bucket by `dayKey` too.
**History sheet** (`FuelCalendarSheet`, from the date capsule): 450 pt detent, `ground`, own `Grabber`, "History" + Done, the goal note ("Current goal: <goal> · <kcal>"). A 7 × 26 grid of Monday-first weeks, oldest left, scrolling sideways and opening with the current week at the right edge (it centres the selected day only when that day would be off screen): 24 pt cells, radius 6, on a 28 pt pitch; month labels over the column holding the 1st; weekday labels; the selected day ringed (30 pt, 2 pt `ink`), today dotted, future days blank. Tapping a cell closes the sheet and goes to that day. Legend `[■0] Not logged … Off target [■1■2■3■4] On target`, then three `StatTile`s (labels may wrap to 2 lines, equal heights): 7-day average, 30-day average (logged days before today only; "–" when none) and "N of 30" days at level 4 among today−30…today−1. Colours `NT.Colors.heat = [surface2, #693927, #98492B, #CA592C, ember]` for levels 0…4.
**Heat scoring** (`FuelCalendar`, pure; the same JSON vectors run on Android). `p` = kcal eaten in integer permille of the kcal goal (half away from zero, clamped 0…10 000, 0 when the goal ≤ 0). Level 0 = nothing logged; a goal ≤ 0 gives 1. Otherwise `d = |p − 1000|` is compared with the band on its side of the goal (`under` when `p < 1000`, else `over`): `d ≤ b[0]` → 4, `≤ b[1]` → 3, `≤ b[2]` → 2, else 1.

| Goal (profile) | under b[0] / b[1] / b[2] | over b[0] / b[1] / b[2] | Level 4 |
|---|---|---|---|
| Lose fat | 100 / 200 / 350 | 30 / 80 / 150 | 90–103 % |
| Build muscle | 30 / 80 / 150 | 100 / 200 / 350 | 97–110 % |
| Maintain | 50 / 100 / 200 | 50 / 100 / 200 | 95–105 % |

Today, while `p < 1000 − under[0]`, reads as progress instead: `min(3, max(1, p / 250))`; from there on it scores like any day. The grid always uses the **current** goal and kcal target.

`FoodSearchService` (Services, actor): Open Food Facts, header `User-Agent: NoTomorrow/0.1 (markzaluben@proton.me)`, one `fields` list for every request (adds `product_name_en`, `generic_name(_pl)`, `abbreviated_product_name`, `lang`, `nutriments_estimated`). **Text search** goes to search-a-licious, `GET https://search.openfoodfacts.org/search?q=<terms>&langs=pl,en|en&page_size=24&fields=…` (read from `hits`), with Lucene operators turned into spaces (nothing left → no request); a 5xx, timeout, 4xx or undecodable body falls back once to the legacy `cgi/search.pl` (never after a 429, offline or a cancel). At most 10 searches start in any 60 s (a new one waits ≤ 6 s for a slot, else `rateLimited`), and a 429 starts a cooldown (Retry-After clamped to 5–120 s, 60 s default). Debounce 500 ms and ≥ 2 characters are the view's job. **Barcode** `lookup(barcode:locale:)` reads `GET https://world.openfoodfacts.org/api/v2/product/<code>.json?fields=…&lc=<app language>` for each form from `barcodeForms` (8/12/13/14 digits; 13 or 14 with a leading 0 also without it; 12 also with a 0 in front) and returns `BarcodeLookup`: `.found(candidate)` as soon as a form has usable nutrition, `.partial(ProductStub)` when a form only had a name (the first stub wins, and a later failing form keeps it), else `.notFound`. A 429 or 5xx is retried once after 1.5 s. Every result, partial and not-found included, is cached 5 min per language. Name chain (`displayName`, pl): `product_name_pl` → `product_name` (only when `lang == pl`) → `product_name_en` → `product_name` → `generic_name_pl` → `generic_name` → `abbreviated_product_name` → "brand quantity"; en starts from `_en`. Nutrition (`per100`): `nutriments` when it has energy (kcal, else kJ / 4.184), else `nutriments_estimated` (the candidate's `isEstimated`, shown by `PortionSheet` as the `fuel.estimatedNutrition` caption and not persisted); the block used must pass kcal 0…950 and P/C/F 0…100, or the product becomes a partial stub. `FoodSearchError`: `rateLimited` (429), `busy` (5xx), `offline` (no connection → `error.network`), `unreachable` (timeout, DNS, TLS, other status → `fuel.search.error.network`), each with its own message.

```swift
protocol BackendClient {

  func signIn(google idToken: String) async throws -> Session
  func signIn(username: String, password: String) async throws -> Session

  func pair(withCode: String) async throws -> Partner

  func partnerState() async throws -> PartnerState           // schedule, attendance for the week, unread heads-ups
  func setAttendance(day: Date, status: AttendanceStatus, reason: String?, note: String?, makeUpDay: Date?) async throws
  func sendHeadsUp(kind: HeadsUpKind, text: String, sessionDay: Date) async throws
  func registerPushToken(_ token: Data) async throws
  func estimate(imageJPEG: Data, meal: MealSlot, locale: String, anthropicKey: String?, notes: String) async throws -> AIEstimate

```
`Session { accessToken, refreshToken, userId }` stored in Keychain by `AuthStore`. `MockBackendClient` implements everything in memory (its `estimate` deliberately keeps the v1 shape, standing in for an old server). `AIEstimate` / `AIFood` decode the v2 answer (`per100`, `portionCount`, `portionUnit`, `gramsPerUnit`, `nutritionSource`, `totals`, `skipped`, …) leniently and still accept v1; `notes` is capped at 1500 UTF-16 units, as the server counts. A `URLError.timedOut` surfaces as `BackendError.timedOut` (same "No connection" copy outside the AI flows). The wire format is in `docs/backend.md`.

## Things that are NOT negotiable

- Rest timer state = `RestTimerController` only. Never run your own `Timer` for it; render remaining time with `TimelineView(.periodic(from: .now, by: 1))`.
- No health data leaves the device except the AI photos (plate or nutrition label, with the typed details; explicit user action) and the user's own attendance and schedule (to the backend while signed in).
- A store that fails to open is never replaced silently: no in-memory fallback, and only the user's "Start with empty data" moves the files — it never deletes them. Every new `@Model` property must be optional or have an inline default.
- AI prompts, schemas and limits come from `backend/data/ai/estimate-spec.json`; change them there, never in Swift, and keep `AIFinalizer` passing every shared fixture.
- Every user-visible string localized in both languages. Every number through `Fmt`.
- Keep files under ~400 lines; split views into subviews in the same folder.
